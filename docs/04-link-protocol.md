# Протокол RP2040-Zero ↔ Guition (ПРЕДЛОЖЕНИЕ, не стандарт)

Готового стандарта нет: оба конца пишем сами. Канал — **UART 3,3 В** (Guition IO17/IO18 ↔ RP2040 GP0/GP1).
Предложение ниже — простое, отлаживаемое на хосте и быстрое для растра.

## Физика

- 8N1, старт **460800 бод** (RP2040 и ESP32-S3 держат до ≥ 921600). Подъём до 921600 — по результатам теста.
- Нужны только TX, RX, GND. Аппаратный flow control не используем; вместо него — окна/кредиты (ниже).

## Кадр

Использовать **COBS + разделитель 0x00**:

```
[ COBS( TYPE:u8 | SEQ:u8 | LEN:u16le | PAYLOAD | CRC16:u16le ) ] 0x00
```

- COBS убирает нули из тела → 0x00 — надёжный разделитель, ресинхронизация после мусора за один байт.
- CRC16-CCITT (poly 0x1021, init 0xFFFF) считается по `TYPE|SEQ|LEN|PAYLOAD`.
- Максимальная полезная нагрузка кадра: **512 байт** (степень двойки, влезает в буфер RP2040).
- `SEQ` — счётчик кадров отправителя (для обнаружения потерь и сопоставления ACK).

Альтернативы, которые рассматривались:
- JSON-lines — удобно отлаживать, но тяжело для растровых данных (хотя можно base64).
- SLIP — аналогично COBS, но с раздувом при частых 0xC0.
- Modbus RTU — избыточно, адресация не нужна.
- I2C/SPI — требуют больше пинов; UART достаточно.

## Сообщения RP2040 → Guition

| TYPE | Имя | Payload | Описание |
|---|---|---|---|
| 0x01 | HELLO | `fw_ver:u16, caps:u16` | При старте и по PING |
| 0x02 | KEY | `code:u8, state:u8` | code = row*4+col (0..31); state: 1=down, 0=up |
| 0x03 | PRINTER_STATUS | `flags:u8, credit:u16le` | b0=busy(DTR), b1=bytes pending, b2=error; credit — свободно в очереди RP2040 (шлётся при изменении, не чаще раза в 20 мс) |
| 0x04 | ACK | `seq:u8, credit:u16` | Подтверждение + сколько байт можно слать дальше (окно) |
| 0x05 | NAK | `seq:u8, code:u8` | Ошибка CRC/переполнение |

## Сообщения Guition → RP2040

| TYPE | Имя | Payload | Описание |
|---|---|---|---|
| 0x10 | PING | — | Проверка связи → HELLO |
| 0x11 | PRINT_RAW | `data` | Сырые байты в принтер (ESC/POS), за вычетом flow control |
| 0x12 | PRINT_BEGIN | `width_bytes:u8, rows:u16` | Начало растра, заранее сообщает размер (RP2040 готовит `GS v 0`) |
| 0x13 | PRINT_ROWS | `data` | Строки растра (кратно width_bytes) |
| 0x14 | PRINT_END | `feed_lines:u8` | Конец; RP2040 может добавить подачу бумаги |
| 0x15 | PRINTER_CFG | `baud:u32le, heat_n1,n2,n3:u8` | Скорость UART к принтеру; затем RP2040 шлёт принтеру `ESC @` и `ESC 7 n1 n2 n3` (ESC @ — только после смены скорости) |
| 0x16 | KEY_CFG | `debounce_ms:u8` | Параметры сканирования клавиш |

RP2040 сама пакует вызов `GS v 0` из `PRINT_BEGIN`+`PRINT_ROWS`; для чего-то нестандартного — `PRINT_RAW`.

## Flow control между платами

- Кредитная схема: RP2040 в каждом ACK сообщает, сколько байт её очередь печати ещё примет.
- Guition не шлёт данных больше выданного кредита. Так не нужен аппаратный RTS/CTS и нет переполнений.
- DTR принтера читает только RP2040; Guition видит это как рост/падение кредита и флаги PRINTER_STATUS.

## Клавиши на RP2040

- Скан матрицы 8×4 каждые ~1–2 мс, дебаунс 5–10 мс (параметр KEY_CFG).
- Отправка событий KEY по переходам (down/up), а не опросом.
- Авто-повтор — на стороне Guition.

## Почему без оптимального варианта «просто UART проброс»

Можно было бы пробросить принтерный UART напрямую через Guition (IO17/18 как принтерный порт), но тогда
RP2040 пришлось бы подключать другим каналом, а клавиатуре не хватило бы пинов. Поэтому принтер
сидит на RP2040, а Guition шлёт ему готовые данные.

## Реализация (prototype/)

Прототип в `prototype/` реализует этот протокол (src/common/frame.js, messages.js). Уточнения, принятые там:
- Окно: Guition считает «эффективный кредит» = последний credit (ACK/STATUS) − стоимость ещё не подтверждённых кадров.
- Стоимость кадра в очереди RP2040: PRINT_BEGIN = 8 байт (`GS v 0` заголовок), PRINT_END = 3 байта (`ESC d n`), остальные — длина payload.
- Печатные задания (растр и RAW) сериализуются на стороне Guition, чтобы сырые команды не вклинивались в растр.
- Размер кадра PRINT_ROWS: до 240 байт (5 строк по 48 байт).
